## 2. 验收场景

### V1 · 未配置（本机当前状态）

```bash
# 确认没有 key
env | grep DEEPSEEK_API_KEY || echo "no key"
curl -s -X POST localhost:3000/api/llm/ping
```

期望：

```json
{ "configured": false }
```

页面：目标页点「测试连接」→ 显示「未配置 DEEPSEEK_API_KEY / SDL_LLM_*」的指引，**没有** 500、没有网络请求到上游。

### V2 · 真实冒烟（key 到位后）

```bash
export DEEPSEEK_API_KEY=...      # 或写进 .env.local（不进版本库）
npm run dev
```

- 点「测试连接」→ 显示 `deepseek-chat · 1234ms`（数字随网络变化）；
- `curl -X POST localhost:3000/api/llm/ping` → `{"configured":true,"ok":true,"model":"deepseek-chat","durationMs":...}`。

### V3 · 错误 key

```bash
export DEEPSEEK_API_KEY=sk-invalid
curl -s -o - -w "\n%{http_code}\n" -X POST localhost:3000/api/llm/ping
```

- 状态 502，body `{"error":{"code":"LLM_AUTH",...}}`；
- body 与日志里都**不出现** `sk-invalid`；
- 页面显示可读错误，不是白屏。

### V4 · 离线契约

```bash
npm test
```

- 全程无真实网络；
- 每个用例的假 `fetch` 都记录了调用次数，重试类用例能断言「恰好 N 次」。

### V5 · 结构化输出的修复

单测覆盖两条：

- 第一次返回 `{ "nodes": "oops" }`（不合 schema）→ 第二次返回合法 JSON → 成功，且第二次消息里带字段路径；
- 两次都不合 schema → 抛 `LLM_BAD_RESPONSE`，消息含 `nodes` 路径。

### V6 · 流式

单测覆盖：

- fixture 按 1 字节切块（最坏情况）→ 拼接结果与整段一致；
- `[DONE]` 后迭代器结束；
- 中途 abort → 不抛未处理异常、迭代器结束。

### V7 · 预算与输入上限

- 断言请求体 `max_tokens === 16000`；
- 构造 100001 字符输入 → `LLM_BAD_INPUT`（400），且假 `fetch` 调用次数为 **0**。

## 4. 不通过的样子

- 测试里真的调用了 DeepSeek（哪怕只有一条）。
- 没有 key 时 ping 返回 500，或页面把「未配置」显示成「连接失败」。
- 错误响应里带 key 片段、上游原始报文或请求头。
- 把 ping 做成 GET，或页面加载时自动调用。
- 把「结构修复重试」写成无限/多次，或与传输重试混成一个计数。
- SSE 解析假定一次 `read()` 就能拿到完整行。
- 输入超限时先发请求再报错。
- 为通过测试放宽既有 201 条用例。

## 6. 评审者 5 分钟检查单

1. 没有 key 时点「测试连接」：是「未配置」还是「失败」？打开网络面板，有没有请求发到 `api.deepseek.com`？
2. 用错 key 再点一次：状态码是 502、code 是 `LLM_AUTH` 吗？响应里能搜到 key 吗？
3. `npm test` 期间断网（或看测试代码）：有没有任何真实网络调用？
4. 看修复重试的测试：是「恰好一次」还是「循环到成功」？
5. 看 SSE 测试：有没有覆盖「半行到达」和「中途 abort」？
