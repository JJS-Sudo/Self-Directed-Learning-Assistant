## 实施记录（2026-10-31）

T1–T5 完成；T6 除「真实 key 冒烟（G3）」外全部完成。用例从 201 增至 **227**。

| 项     | 结果                                                                              |
| ------ | --------------------------------------------------------------------------------- |
| 配置   | `LlmConfig` 类；key 放在私有字段，`String()` / `JSON.stringify()` 都不带出        |
| 非流式 | 原生 `fetch`、`AbortSignal` 超时、5xx/429 退避重试、401/403 不重试                |
| 流式   | 按行缓冲解析 SSE，支持半行分块与中止                                              |
| 结构化 | zod 校验 + **恰好一次**修复重试，失败带字段路径                                   |
| ping   | `POST /api/llm/ping`；未配置 200 `configured:false`，**0 次上游请求**；GET 是 404 |
| 页面   | 目标页「测试连接」按钮，点击才调用；未配置显示环境变量指引                        |

实测证据：

- 无 key：`POST /api/llm/ping` → `{"configured":false,"ok":false}`，200；`GET` → 404；
- 页面点「测试连接」→ 显示「未配置：设置环境变量 DEEPSEEK_API_KEY 后重启服务」，
  网络面板只有 `localhost:3100`，没有到 `api.deepseek.com` 的请求；
- 测试：32 个文件 / 227 用例全绿，全部走注入的假 `fetch`，零真实网络；
- 错 key → 502 `LLM_AUTH`，响应不含 key 与上游报文（用例断言）。

**真实冒烟（2026-10-31，key 由使用者提供，未落盘）**：

- `POST /api/llm/ping` → `{"configured":true,"ok":true,"model":"deepseek-flash","durationMs":747}`；
- 页面点「测试连接」→「连接正常 · deepseek-flash · 599ms」；
- 响应体里搜不到 `sk-` 前缀，密钥没有进入任何响应或日志；
- 用无效 key 再打一次 → **502** `{"code":"LLM_AUTH"}`，响应里搜不到无效 key；
- 观察：上游返回的 `model` 是 `deepseek-flash` 而非配置里的 `deepseek-chat`（账号侧的模型映射）。
  客户端以**响应里的 model** 为准，页面不写死配置值。

与计划的偏差：

1. **`SDL_LLM_MAX_RETRIES=0` 原先被当成非法值**回落到 3 —— 被「限流只调一次」的用例抓出来，
   改成允许 0（关掉重试）。
2. **超时不重试**：超时已经耗掉 120s，再重试只会让用户体验更差；只有 5xx/429/网络错误重试。
3. **流式一旦出字就不再重试**（否则会重复输出）；连接阶段失败仍按 `LlmError` 抛出。
4. 非 401/403/429 的其它 4xx 归入 `LLM_UPSTREAM`（502），对前端只意味着「上游不可用」。
